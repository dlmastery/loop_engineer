# Harness Project Skills

An agent starts every run cold and fills any hole in your intent with a
confident guess. A skill is that intent written down on the outside — the
conventions, the build steps, the "we don't do it like this because of that one
incident" — captured once, read every run. Without project skills, the loop
re-derives your whole project from zero every cycle. With them, intent compounds
instead of being re-paid each session.

## What deserves a skill

Write a skill for anything a competent newcomer would get wrong by guessing:
- **Conventions** that aren't enforced by a linter (naming, layering, error
  handling, what "done" looks like for a feature).
- **Workflows** with non-obvious steps (how to add a migration, cut a release,
  add an endpoint, regenerate a client).
- **Scar tissue**: "we don't do X because of Y" — the decisions that look wrong
  until you know the incident behind them.
- **Domain rules** the code assumes but never states.

Don't write a skill for what the repo already records well (code structure git
shows, anything in `CLAUDE.md`, autogenerated docs). Duplicated intent rots.

## Authoring (Claude Code format)

Skills are a folder with a `SKILL.md` at `.claude/skills/<name>/SKILL.md`, plus
optional `scripts/`, `references/`, `assets/`. Only `name` and `description` are
required frontmatter.

```markdown
---
name: add-api-endpoint
description: How to add a REST endpoint in this repo — routing, validation, tests, and the error-envelope convention. Use when adding or modifying an endpoint under src/api.
---

# Add an API endpoint

1. Route goes in `src/api/routes/` and is registered in `src/api/index.ts`.
2. Validate input with the shared `zod` schemas in `src/api/schemas/` — never
   hand-roll validation (incident 2025-11: unvalidated body shipped to DB).
3. Errors use `errorEnvelope()`; never return raw exceptions.
4. Every endpoint needs a test in `test/api/` covering the 4xx path.
```

### The description is the trigger
Triage and autonomous matching live or die on the `description`. A tight,
boring, literal description beats a clever one — it should name *what* and the
*when* (the files, the task) so the right skill fires unprompted. Front-load the
trigger words.

## Skill vs plugin

The skill is the **authoring** format. When you want to share skills across
repos or bundle several together, package them as a **plugin** (`loop-connectors`
covers shipping). Author here; ship there.

## Done when

- A newcomer (or cold agent) could work in each major area by reading a skill,
  not by asking you.
- Each skill's `description` clearly states what + when, so it fires on the
  right task without being named.
- `CLAUDE.md` points at `.claude/skills/`.

Then move to `harness-verification`.
